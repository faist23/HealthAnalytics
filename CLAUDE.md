# HealthAnalytics — Claude Code Instructions

## Design System
Always read `DESIGN.md` before making any visual or UI decisions.
All colors, typography, spacing, and aesthetic direction are defined there. Do not deviate without explicit user approval.

In QA mode, flag any code that uses hardcoded hex values, system default colors (`Color.green`, `Color.orange`, `Color.blue`, `Color.red`, `Color.purple`, `Color.yellow`, `Color.pink`, `Color.cyan`, `Color.gray.opacity(...)`), or inline font sizes instead of the design tokens defined in `DESIGN.md`.

Note: `MainTabView.swift` uses a legacy `AppColors` struct and is intentionally excluded from the token sweep until the tab system is refactored.

The primary design direction is **Signal Indigo**: cool dark surfaces (`#09090E` background), electric violet accent (`#7C5CFC`), SF Pro Rounded for hero numerals, SF Pro Text for coaching voice, SF Pro Mono exclusively for raw data/chart annotations.

## Architecture
See `GEMINI.md` for the full engineering mandate. Key rules:
- All readiness logic lives in `ReadinessRepository` — never in ViewModels
- Use `DataFingerprint` caching to prevent score drift
- ACWR sweet spot: 0.8–1.3

### Key extension points (v0.1.9.0)
- **Five-tab IA** (v0.1.9.0). The tabs are Coach (0) / Recovery (1) / Load (2) / Patterns (3) / Labs (4). Each answers exactly one question and Phase 2.4's voice rule still holds: Coach is the only tab with advisory voice (Master Coach paragraph); Recovery / Load / Patterns / Labs are descriptive dashboards. **Coach** = "what should I do today?" **Recovery** = "how recovered is my body and why?" **Load** = "am I building or breaking down?" **Patterns** = "what has my body been doing lately?" **Labs** = "what experimental signal is the app studying?" When adding new content, name the tab whose question it answers — don't dump it where it'll be seen. The `Labs` tab is intentional exploration, not a graveyard for unfinished work; only ship features there you actively want users to evaluate.
- **"Recovery" vs "readiness" vocabulary**. The score is a *recovery* measure (HRV, RHR, sleep, carry-forward fatigue) and all user-facing copy must call it "recovery" / "recovery score". "Ready"/"readiness" verdict language is allowed ONLY in Coach-tab prose (MasterCoachEngine output), as a conclusion drawn from recovery + load together. Internal identifiers (`UnifiedReadiness`, `ReadinessRepository`, `ReadinessViewModel`, `morningReadinessScore`, UserDefaults keys, notification names) intentionally keep the old name — do not rename symbols, and do not let internal names leak into UI strings. Folding ACWR into the score to make "readiness" literal was considered and rejected (pollutes the physiological measure, breaks the recovery-model hierarchy).
- **Tab indices** are defined in `TabCoordinator` (`coachTab`/`readinessTab`/`loadTab`/`patternsTab`/`labsTab`) and must match `.tag(N)` in `MainTabView`. `readinessTab` is the Recovery tab (internal constant keeps the old name). The `intelligenceTab` alias points to `patternsTab` for one release cycle; remove after v0.2.0.
- **Patterns tab affordances** (v0.1.9.0). Active pattern count is surfaced as a numeric `.badge(N)` on the Patterns tab icon (`MainTabView` queries `TrainingPattern` directly) AND as a plain header strip at the top of the tab. Two consumers of the same signal — both filter on `TrainingPattern.isActive` (window `activeWindowDays`, 10 days), so keep them on it if you change the window. The Patterns tab owns the only `ScrollView` on its surface; `InsightsView` is a pure content producer (`VStack`, no `NavigationStack`/`ScrollView`/`ScrollViewReader`). Don't re-introduce a nested `ScrollView` in either view — the `ScrollViewReader.proxy.scrollTo(patternType)` cross-tab deep-link relies on the single-ScrollView guarantee.
- **Repository-driven data flow** (v0.1.8.0 architecture refactor — see `REFACTOR_PLAN.md`). `ReadinessRepository.shared.bootstrap()` is called once from `HealthAnalyticsApp.swift` and subscribes to `DataSyncCompleted` centrally — **views never listen for sync, never call `analyze()`, never fetch SwiftData**. Each app-lifecycle sync trigger (`.task` on launch, `.onChange(scenePhase)` on scene-active, Strava OAuth callback) explicitly calls `ReadinessRepository.shared.refreshIfNecessary(modelContext:)` after `SyncManager.performSmartSync()` to cover the 30-min throttled-sync path where no notification fires. `UnifiedReadiness` carries every value a view could need (including per-tab data like `cardiovascularStrain`, `holisticMetrics`, `todayWorkouts`, `todaySteps`, and the raw chart arrays `hrvData`/`rhrData`/`sleepData`/`stepCountData`/`workouts`/`weightData`). `ViewModels` are Combine subscribers — they observe `$currentReadiness`, `$analysisError`, `$isAnalyzing` and republish. **Do not add SwiftData fetching to a ViewModel or a view; add the field to `UnifiedReadiness` and compute it inside `performFullAnalysis`.**
- **Refreshes requested mid-analysis are coalesced, never dropped**. `performFullAnalysis` still guards on `isAnalyzing` (concurrent runs interleave SwiftData writes), but it now sets `pendingRefreshRequested` and re-calls `refreshIfNecessary` on the way out. A run is slow (ML training, `MasterCoachEngine`, HealthKit reads) and a workout finishing sync lands inside that window — the old bare `return` discarded the `DataSyncCompleted` refresh, leaving the published snapshot describing pre-ride data until an unrelated trigger came along. The re-entry re-fingerprints, so it's a no-op unless the store actually moved.
- **User-initiated sync** bypasses both throttling layers. `SyncManager.performSmartSync(force: true)` skips the 30-minute throttle; `ReadinessRepository.forceRefresh(modelContext:)` skips the fingerprint cache. Use both together on any user-initiated refresh affordance (pull-to-refresh, toolbar refresh button) so a deliberate tap always does visible work. Background and lifecycle triggers should use the default (un-forced) paths.
- **Historical ACWR calls `calculateReadiness(..., referenceDate:)`** with the date being asked about — not `Date()`. The default `referenceDate: Date()` keeps current-assessment callers behavior-stable; historical callers (the ACWR trend chart, `PerformancePredictor` training rows) must pass an explicit reference date or the inner methods will window `[today-7, today]` / `[today-28, today]` regardless of the workout-filter intersection.
- **Cardio Load gauge has no synthetic fallback** (v0.1.8.0). When `viewModel.cardiovascularStrain` is `nil`, the gauge shows an explicit "needs watch data" empty state. **Never reinstate the `acwr * 10` fallback** that previously fabricated a strain value from training-load ratio — it presented an authoritative-looking number with no physiological basis.
- **Coaching voice lives only on the Coach tab** (v0.1.8.0). The Master Coach paragraph (`UnifiedReadiness.coachAdvice`) renders only via `DashboardViewModel.readinessRecommendation` on `CoachTabView`. Recovery and Load show descriptive captions of their own state (`readinessDescription(for:)` in `RecoveryTabView`, `loadDescription` in `StrainTabView`) — facts, not advice. Intelligence's `InsightsView` "Today's Signal" card shows pattern counts. **Don't add another consumer of `coachAdvice` outside Coach** without re-opening that decision. The rule extends to `TrainingLoadCalculator.recommendation` / `LoadVisualizationData.LoadSummary.recommendation`: both are advisory ("Add recovery days regardless of how you feel"), and as of 2026-08-05 neither renders on a Load surface — `UnifiedTrainingLoadCard` shows only its `interpretation`, and `LoadSummaryCard` (Extended Analysis) shows a `loadDescription` worded identically to `StrainTabView.loadDescription`. They still render on `METActivityCard` and `InsightsView`.
- **Dynamic Master Coach Engine** — `Services/Coaching/MasterCoachEngine.swift`. Generates a single, cohesive coaching paragraph. `ReadinessRepository` computes the `morningReadinessScore` by functionally omitting today's workouts, passing it to the engine to explicitly highlight intra-day fatigue deltas.
- **NEAT Mechanism 1 (excess steps add to intra-day strain)** — `RecoveryDecayService.calculateIntraDayReadiness(morningReadiness:workouts:sleepHours:todayStepExcessTSS:)` accepts a `todayStepExcessTSS` parameter. `ReadinessRepository` computes it as `min(excessSteps / 3000.0, cap)` where cap = 20% of today's workout TSS (or 2.0 on rest days). Step baseline is the 30-day rolling average daily step count; fallback `5000` when no history exists. Flows into `EnergyBankChart` via `UnifiedReadiness.todayStepExcessTSS`.
- **NEAT Mechanism 2 (overnight recovery rate modifier)** — `RecoveryDecayService.overnightRecoveryMultiplier(workoutTSS:stepExcessTSS:)` returns a [0.5, 1.0] multiplier applied to the prior-day fatigue half-life (16h → up to 32h). Only activates when combined workout strain + step excess exceeds threshold. Does not activate on step excess alone. `ReadinessRepository` derives the multiplier from yesterday's load and flows it through `UnifiedReadiness` → `ReadinessViewModel` → `EnergyBankChart`.
- **New patterns** — extend `PatternType` enum in `Models/TrainingPattern.swift`, add a `detectX()` method to `Services/Analytics/TrainingDNAAnalyzer.swift`, wire it in `upsertPatterns()`. Pattern data flows through `StoredDailyScore` snapshots (upserted after every analysis run via `ReadinessRepository.upsertDailyScore()`). `StoredDailyScore.dailyLoad` stores the total TSS-equivalent load for the day (sum of `calculateWorkoutLoad()` across all workouts). Hard-day detection in `detectBackToBackReadinessCrash()` uses `dailyLoad >= 1.0` — do not revert to `workoutCount >= 1` (warmup rides score < 0.5 TSS and must not count as training days). Sick-day proxy detection in `detectHRVPrecursor()` counts a day as rest only when its `StoredDailyScore` row exists with `dailyLoad < 0.5` (not `fetchWorkoutDays`) — do not revert to a HealthKit workout-presence check, as it would permanently block the pattern for users who do daily warmup rides (~0.17 TSS). A missing row is unknown, never rest: the background pass writes rows only through its guarded post-sync Coach refresh, and a ride with no row yet reads as a low-step day (`testHRVPrecursor_dayWithoutAScoreRowIsNotASickDay`). A day's load is its highest row (a 0.0 twin beside the ride's row is not rest), and a stored workout with load >= 0.5 that day vetoes rest even when the row says 0 (a row written mid-morning keeps a later ride at 0; the workout store's duplicates and misses can only make rest less likely) (`testHRVPrecursor_zeroTwinBesideARideRowIsNotRest`, `testHRVPrecursor_storedRideOnAZeroLoadRowDayIsNotRest`). The Peak Form streak counts a duplicate-day day once, only if every row is in the sweet spot. Likewise `detectPerformancePeak()`'s ACWR streak counts calendar days ending yesterday, not rows; a missing or stale day ends it (`testPerformancePeak_missingDayEndsTheACWRStreak`, `testPerformancePeak_staleNewestRowGivesNoACWRStreak`).
- **Every pattern surface filters on `TrainingPattern.isActive`**. Nothing deletes a `TrainingPattern` — `upsertPatterns()` only inserts and updates, deliberately, so `notificationSent` survives. Recency is therefore the ONLY signal that a pattern still holds, and `isActive` (detected within `TrainingPattern.activeWindowDays`, 10) is the single definition. `InsightsView` rendered the Training DNA card list unfiltered, so a taper detected once kept claiming "Taper Underway / Load down 41%" three weeks later while the tab badge and the Patterns header strip — both already filtered — read 0. Do not re-introduce a local `sevenDaysAgo` cutoff in a view; all six read sites (`MainTabView` badge, `PatternsTabView` header strip **and both deep-link `contains` checks**, `RecoveryTabView.topActivePattern`, `InsightsView` card list, and `ReadinessRepository`'s `activePatternTypes` feeding `MasterCoachEngine`) read `isActive` so the window moves in one place. The `PatternsTabView` deep-link checks matter separately: only active patterns get an `.id(patternType)` in the hierarchy, so a `contains` hit on a stale row makes `proxy.scrollTo` fire at a missing ID and skips the stash-and-retry branch. **`activeWindowDays` (10) MUST stay strictly greater than the 7-day analysis cadence (`ReadinessRepository.patternAnalysisStalenessInterval`)** — at exactly 7 they coincided and patterns expired at the instant their refresh became eligible. **The active pattern set is part of the cache key.** `activePatternTypes` is baked into `UnifiedReadiness.coachAdvice` inside `performFullAnalysis`, and a pattern expiring changes no data count — so on fingerprint alone the Coach paragraph outlived the card for up to a day. `refreshIfNecessary` now reuses the snapshot only when `ReadinessRepository.canReuseCachedAnalysis` agrees on fingerprint, calendar day, AND the active set (`lastActivePatternTypes`). The check runs on every refresh trigger (launch, scene-active, sync) and at the end of every successful `runPatternAnalysis` that finishes while the app is in the foreground (`isAppInForeground`; a run finishing in the background defers it to the next foreground). A Coach tab left open across the expiry instant updates on the next trigger. Covered by `ReadinessRepositoryCacheTests`. `TrainingSignatureCard` intentionally reads `.backToBackCrash` unfiltered — it describes a long-lived trait, not a this-week signal. Covered by `TrainingDNAAnalyzerTests` "Pattern Staleness".
- **Store-based pattern checks read complete days ending yesterday.** `TrainingDNAAnalyzer.completeDaysEnd` (start of today) and `completeDayStart(daysBack:)` bound every `StoredDailyScore`/`StoredWorkout` read in the HRV precursor sick-day proxy (180 days), back-to-back crash (90), performance peak (90) and taper (28), so a half-finished today can neither fake nor hide a pattern; today is left out until it is complete. The sick-day proxy's live HealthKit steps are filtered to complete days too (`date < completeDaysEnd`): today's count is partial, and yesterday + a 9am today both read under 2000 and formed a fake sick-day window (`testHRVPrecursor_todaysPartialStepsCannotFormASickWindow`). Live HealthKit series (HRV, RHR, sleep) still include today, so the latest HRV reading is used. Do not use `Date()` as the upper bound in a new store-based check.
- **Analysis is repository-owned; callers can await it but never cancel it** (`Utilities/SingleFlight.swift`). Every caller is a view `.task` / `.refreshable` or an app lifecycle task, and SwiftUI cancels those on a tab swipe. A cancelled `performFullAnalysis` used to make `MasterCoachEngine.synthesizeWithLLM`'s `Task.sleep` throw, fall back to the heuristic paragraph, and cache it for the day. `refreshIfNecessary` / `forceRefresh` now run it through `SingleFlight.shielded` (keeping the `isAnalyzing` / `pendingRefreshRequested` coalescing — a request mid-run must re-run, not join), and `runPatternAnalysis(container:trigger:)` runs through `patternAnalysisFlight` (overlapping requests join one run). The `PatternAnalysisTrigger` decides the throttle (`shouldRunPatternAnalysis`): `.appear` (Recovery tab) and `.background` skip a run within `forcedPatternAnalysisMinInterval` (5 min) of the last success, `.staleCheck` (InsightsView) waits out `patternAnalysisStalenessInterval` (7 days, must stay under `activeWindowDays`), and `.userRetry` ("Try again") always runs. The Coach refresh after pattern analysis is a plain `await` inside that run. **Don't call `performFullAnalysis` or `TrainingDNAAnalyzer.analyze` directly from a view or task handler.** The app-refresh handler in `HealthAnalyticsApp` (`.backgroundTask(.appRefresh(...))`) reschedules itself first, then calls `runBackgroundPass(container:wake: .appRefresh)` (see the background-pass bullet below); the pass, not the handler, owns the locked-device guard and the `.background` throttle. Whether a run refreshes Coach and reports errors is decided when it finishes, from `isAppInForeground` (UIApplication state; overridable in tests), never from who started it or who joined it — the trigger only picks the throttle. That's deliberate: trigger-based reporting needed joiner bookkeeping that review kept finding holes in (a background run resuming after the user reopens the app, a cancelled joiner refreshing early, a start race). Joiners do nothing after joining. Don't refresh after a throttled skip: `refreshIfNecessary` can run `backfillHistoricalScores`, which clears `lastPatternAnalysisDate` when it inserts rows, and an unconditional clear would defeat the throttle. It clears only then because it also runs inside the Coach refresh after a successful pattern run, and an unconditional clear erased that run's own stamp for anyone the backfill keeps re-checking (a day with no sleep data never gets a row, so it reads as a gap; a skipped day). A cancelled caller stops *waiting* immediately (the background budget expiring needs the handler to return) while the work runs on.
- **Background pattern pass: two triggers, one pass.** `BackgroundPatternPass` (`Services/Analytics/BackgroundPatternPass.swift`) is the only thing background triggers run, entered through `ReadinessRepository.runBackgroundPass(container:wake:)`. Triggers: (1) HealthKit background delivery for HRV and workouts (`HealthDataObserver`, `.immediate` frequency), registered from `AppDelegate.didFinishLaunching` at every launch once onboarding is complete (a delivery wake relaunches the app and the observer queries must exist before it returns, so registration can't wait for the SwiftUI `.task`) and from the `.task` right after onboarding finishes; the handler always calls its completion, whatever happens. It holds UIApplication background time around the pass (`HealthDataObserver.runHoldingBackgroundTime`, name `patternPass`) so the completion isn't left pending across a suspension: on expiry it cancels the task *waiting* for the pass (`SingleFlight` returns it at once; the flight's work runs on and the commit gate covers a resume), the observer completes, and the identifier is ended exactly once whichever side ends it first. Covered by `HealthDataObserverTests` through the `BackgroundTime` seam. An observer-query error completes immediately and logs in DEBUG. (2) The app-refresh task as backup. **A wake while the app is in the foreground skips the pass** (`BackgroundPatternPass.skipIfForeground`, outcome `skippedForeground`, recorded after the wake and before the flight, and checked again by the flight's `shouldStart` gate, `BackgroundPatternPass.shouldStart`, which is the check that matters: a wake that joined an abandoned pass starts a run of its own later, maybe after the user opened the app, and that retry must skip too. `SingleFlight` asks `shouldStart` only right before it would start a run, with no await before setting `current`, so a declining wake starts nothing a foreground caller could join; that caller runs its own analysis (`test_foregroundJoinerBehindASkippingWakeRetry_runsItsOwnWork`, a race that failed about 1 run in 50 before the gate); pinned by `BackgroundPatternPassTests`): iOS fires every observer query once when it registers, so every foreground cold launch "delivered" and ran a full pass the foreground's own sync and refresh already cover. App-refresh wakes are background by construction. Order: protected-data guard (`skippedLocked`), `.background` throttle (`throttled`, 5 min), rewrite guard (`skippedSyncing` while `SyncManager.isRewritingStore`: a sync, the one-time workout dedup or the power-zone backfill, which runs after a sync or an FTP edit; a ride with no watts stream is marked `SyncManager.noPowerStreamCSV` so the backfill stops re-fetching it and holding the flag after every sync; the first such answer writes `noPowerStreamRetryMarker` (`"retry:<time of the miss>"`) instead, re-fetched once a day after the miss and ahead of the backfill's 50-ride cap, since a stream may not be processed when the ride reaches Strava, which can be days after the ride; the retry's miss writes the permanent marker, and an FTP edit can clear a pending retry for one more fetch; pinned by `NoPowerStreamMarkerTests`), HealthKit-only workout refresh (`SyncManager.refreshWorkoutsFromHealthKit`), detection behind a commit gate, stamp `lastPatternAnalysisDate` (key `ReadinessRepository.lastPatternAnalysisKey`, shared with the foreground run) with the START time, then a guarded Coach refresh. **The pass never fills score rows ahead of the Strava sync.** Its commit gate refuses (`abandoned`) when a store rewrite is running at commit OR `SyncManager.storeRewriteGeneration` moved since the pass started (a quick sync can start and finish inside detection). Coach is refreshed (`refreshIfNecessary`, whose backfill fills rows) only when `BackgroundPatternPass.mayRefreshCoach`: app in the foreground, no rewrite running, and the last sync ran within `SyncManager.smartSyncMinInterval` (30 min): the same state the foreground's own post-sync refresh fills rows in (a recent `lastSyncDate` does not prove Strava succeeded; a failed fetch still stamps it). That case matters: opened soon after a sync, `.active`'s sync is throttled and its Coach refresh runs before the pass commits, so without this Coach would miss the new pattern set. In every other foreground case a sync runs, and either the gate refuses or that sync's own refresh sees the commit. An unconditional Coach refresh here (before 38e08fe) filled rows from HealthKit-only loads while the sync waited on the pass; don't restore it. A workout-refresh failure never blocks detection, but the budget is checked after it: a pass that overran `maxDuration` inside the refresh returns `abandoned` before detection (no stamp). **The pass has no fill step of its own**: a background fill would insert rows with Health-only loads before the foreground Strava sync and nothing rewrites rows, so missing rows are filled only by `refreshIfNecessary` after a sync (the foreground's, or the pass's guarded Coach refresh below). **Abandon rule:** the commit gate refuses (`PatternAnalysisError.commitDeclined`, outcome `abandoned`: no patterns, no notification, no stamp; workout rows written earlier in the pass are kept) when detection finishes more than `BackgroundPatternPass.maxDuration` (2 min) after the pass started or the clock moved backwards: a background budget is ~30s, so a longer run spanned a suspension and some reads predate the freeze while others follow it. `insufficientData` stamps and completes; any other error is `failed`, silent and unstamped so the next trigger retries. **Foreground runs use the same gate:** `performPatternAnalysis` passes `commitGate: isWithinBudget(startedAt:now:)`, so a foreground run the user left mid-detection and a delivery wake resumed hours later commits nothing, sends nothing and stays unstamped, and its joiners rerun. **`notificationSent` is saved before any alert is sent** (`TrainingDNAAnalyzer.analyze`: mark, save, then `PatternNotificationService.send`): a wake killed between send and save used to lose the flag and alert again; now a kill costs at most one missed alert. Patterns are marked only when notifications are authorized (`isAuthorized()`), so a later grant still delivers them. **A joiner of an abandoned run runs once more:** `SingleFlight.run`'s work returns whether it completed (`runBackgroundPass`'s work returns `BackgroundPatternPass.isCompleted(outcome)`, false only for `abandoned`, and `runPatternAnalysis`'s work returns false only when its commit gate declined), and a caller that joined a run returning false starts its own work, or joins the fresh run another joiner started, exactly once (the starter never retries, a cancelled joiner just returns). Without it a frozen pass that resumed swallowed every wake and appear that joined it. Pinned by `SingleFlightTests`. **The pass never posts `DataSyncCompleted`, never moves `lastSyncDate`, never calls Strava** (that would make the foreground think a full sync ran, and Strava needs the network and tokens). Its workout refresh (`DataPersistenceActor.upsertHealthKitWorkoutsOnly`) drops any HealthKit ride `WorkoutMatcher` pairs with a stored Strava workout so a Watch+Strava ride isn't stored twice. That check reads the store, so the background upsert and the foreground sync are serialized on `SyncManager` (`BackgroundRefreshGate`, main actor): `refreshWorkoutsFromHealthKit` does nothing (no fetch, no stamp) while `isSyncing`, and `performSmartSync` / `resetAllData` wait for an in-flight refresh right after setting `isSyncing`. Both checks run on the main actor before their first await, so the two can't interleave. The gate is covered by `BackgroundRefreshGateTests` (skip, join, a failing in-flight refresh reaching its joiner); its `SyncManager` wiring has no seam (singleton + HealthKit). The refresh reads from `SyncManager.healthKitRefreshWindowStart` (later of the last background refresh and the last sync, else a week back, minus one day), pinned by `HealthKitRefreshWindowTests`. **Score rows are filled only by the foreground, only when missing; their loads are not recomputed** (see the TODO "A day's load is frozen at the first write"). **Debug counters:** `BackgroundPassLog` (UserDefaults) counts wakes (`hrvDelivery`, `workoutDelivery`, `appRefresh`) and outcomes (`skippedForeground`, `skippedLocked`, `throttled`, `skippedSyncing`, `completed`, `abandoned`, `failed`), plus last outcome, its time and HRV-sample-to-commit latency; Settings → Background Pass shows them (`BackgroundPassStatsView`). A query's first fire in each process is counted as `launch`, not as a delivery (`HealthDataObserver.wakeForFire`): iOS fires every query once when it is executed, so a background cold launch (app refresh, or a delivery relaunch for the other type) "delivers" too; the pass still runs for it but measures no latency. A delivery that relaunches a TERMINATED app is also its query's first fire, so it shows under `launch`, not `hrvDelivery`, and records no latency; the checklist's `hrvDelivery` +1 needs an app that was suspended, not terminated. A foreground skip is counted but never overwrites "last outcome", the checklist's evidence of the last background pass. The one-time workout dedup in `performSmartSync` waits for an in-flight background refresh and blocks new ones (`isMigrating`). Wakes count separately by app state (`recordWake(_:appActive:)`, read with `count(_:whileActive:)`; "active" is `applicationIsInForeground`, i.e. not `.background`, because a cold launch is still `.inactive` when the observers first fire): iOS fires every observer query once when it registers, so a foreground cold launch "delivers", and those wakes show as "(+N while open)", never as delivery evidence; `count(_:)` is the not-active count. Latency is recorded only for `.hrvDelivery` wakes (the pass gets its `wake`), measured to the commit, not to the end of the HRV query after it. Covered by `BackgroundPatternPassTests` against fake steps; `LiveBackgroundPassSteps` and `HealthDataObserver` have no seam (singleton + HealthKit). **Device checklist** (simulator can't run background delivery): lock the phone, add an HRV sample in Health, unlock, and Background Pass shows `hrvDelivery` +1 and an outcome within minutes; cold-launch in the foreground and check whether the delivery counters move (they should move only under "while open", with `skippedForeground` rising alongside); a newly qualifying pattern notifies without opening the app; pausing in the debugger over 2 min mid-pass yields `abandoned` and no notification; a ride recorded on Watch and Strava shows once in Workout Audit after a background wake. **App-refresh scheduling:** `schedulePatternAnalysisTask` submits a `BGAppRefreshTaskRequest` (no sooner than `patternAnalysisMinBackgroundInterval`, 6h), which must match the SwiftUI `.appRefresh` handler. The handler always resubmits (a fired request is no longer pending); leaving the app submits only when none is pending (`schedulePatternAnalysisTaskIfNoneIsPending`), because a submit replaces the pending request and resubmitting on every exit pushed the run 6h out each time, so daily users never got one. The launch `.task` returns after `bootstrap()` when the app is in the background: a background refresh launch can connect the scene, and a locked-device Coach refresh would cache an empty day; `.active` does sync, refresh and the notification prompt instead. The request and the handler both use `HealthAnalyticsApp.patternAnalysisTaskID`, and Info.plist must keep `UIBackgroundModes` = `fetch` plus that id in `BGTaskSchedulerPermittedIdentifiers` (pinned by `BackgroundRefreshConfigTests`). A run that finishes while the app is in the background is silent on errors (HealthKit refuses reads while the device is locked; that must not become an error row) and skips the Coach refresh, which the next foreground does because the pattern set is in the cache key. A HealthKit `errorDatabaseInaccessible` is silent even in the foreground (`isLockedDeviceError`): a run suspended across a lock resumes on unlock and fails for a reason that no longer applies. Pinned by `ReadinessRepositoryBackgroundPatternErrorTests` (skips on an onboarded host, or when the simulator's HealthKit doesn't throw) and `ReadinessRepositoryLockedDeviceErrorTests`. Before v0.1.15 it submitted a `BGProcessingTaskRequest` with no background mode declared, `submit` always threw, and `try?` hid it: the task had never run. Verify on a device, including both scheduling rules above (the simulator can't run BG tasks; no seam). Covered by `SingleFlightTests`, `ReadinessRepositoryPatternThrottleTests` and `ReadinessRepositoryPatternThrottleWiringTests` (skipped on an onboarded simulator host); `ReadinessRepositoryPatternCancellationTests` pins that `runPatternAnalysis` goes through the flight (a cancelled caller's run still finishes; skipped on an onboarded host); only the shielded `performFullAnalysis` call site has no test seam (singleton + HealthKit).
- **Taper detection bands on `dailyLoad`, never `dailyStrain`**. `detectTaperUnderway` compares mean `StoredDailyScore.dailyLoad` (actual TSS/day) over the 7 complete days ending yesterday vs the 21 before that. It previously compared `dailyStrain` (the ACWR *ratio*), which decays toward 1.0 on its own for ~28 days after any increase in training while the 28-day chronic denominator catches up. Simulated over 10 load histories that metric got 5 verdicts wrong: it fired "Load down 41%" at riders who had merely resumed training or stepped up a block and then held it flat (0% real change, Load tab correctly reading ACWR ~1.0), and it MISSED a genuine 50% volume cut (only a 24% ratio move). The load metric got 0 wrong. `taperBaselineLoadThreshold` (0.25 mean daily load over the 21-day baseline) blocks firing when there was no training block to taper from — including pre-migration rows where every `dailyLoad` is 0.0, which would otherwise read as a 100% drop. It is deliberately low for weekend warriors (1.0 ≈ 7h zone-2/week would hide the pattern from most of them); a casual rider's week off is rejected by the Tier 1 session-presence check below, not by this floor — pinned by the pair `testTaperUnderway_casualRiderGenuineTaper_confirmed` (a 0.29 baseline must still fire) and `testTaperUnderway_casualRiderWeekOff_notConfirmed`. The test fixture `makeTaperScores` pins `dailyStrain` to a constant so reconnecting the detector to it goes red.
- **Taper detection corroborates intent with intensity**. Volume down + HRV up cannot distinguish a taper from injury, illness, or a week of work travel. `detectTaperUnderway` therefore gates on `taperIsCorroborated(endingBefore:)` (called with `completeDaysEnd`), which reads `StoredWorkout` over the same 28 complete days in two tiers. **Tier 1** (every user, no sensors needed): at least `taperMinimumRecentSessions` (1) workout in the recent window, the 7 complete days ending yesterday (baseline = the 21 before that; calendar days on both ends, matching the daily scores — a rolling 7×24h/28×24h window made the verdict depend on time of day, and today's half-finished ride is left out until it is complete) — you cannot taper by not training, and this is what catches the crashed rider. **Tier 2** (only when both windows contain a workout with real power/HR): mean intensity over the last 7 days must hold at `taperIntensityRetention` (0.85) of the days 8–28 baseline; volume and intensity falling together is a stoppage, not a taper. Intensity comes from `TrainingLoadVisualizationService.estimateIntensity` — now non-private specifically for this reuse. **Do not reimplement intensity in the analyzer**; duplicated load math is how this project ended up with two disagreeing ACWR engines. `hasIntensitySignal` lives beside `estimateIntensity` and MUST track its fallback chain — comparing a measured window against neutral-5.0 placeholders would fabricate a difference from missing data. Users with no power/HR get Tier 1 only, deliberately: blocking the pattern outright for thin-data users repeats the sick-day-proxy mistake. Analyzer test containers need `StoredWorkout` + `StoredFTPSnapshot` in the schema, and any test asserting a taper FIRES must seed workouts (`seedIntensityHeldWorkouts`) — a load drop alone is no longer sufficient.
- **Taper copy describes the measurement and never asserts intent**. `detectTaperUnderway` fires on volume down ≥30% AND a positive 7-day HRV slope — which is equally the signature of injury, illness, or a week of work travel, since HRV rises on rest either way. The detector has no intent signal, so no taper-facing string may claim one. `PatternType.tapering.displayName` is "Load Dropping" (not "Taper Underway"); `evidenceSummary` leads with "Volume down N% and HRV recovering" and hedges the Mujika & Padilla peak-form projection on "If this is a planned taper"; `coachingResponse` and both `MasterCoachEngine` taper branches (score ≥80 and ≥60, duplicated across the LLM and heuristic paths — four strings) address the involuntary case too. Banned phrases: "Taper Underway", "taper is underway", "Trust the process", "fitness is locked in". Pinned by `testTaperCopyDescribesTheObservationRatherThanAssertingATaper`, `testTaperUnderway_emittedCopyIsConditional`, and the `MasterCoachEngineTests` banned-phrase assertions. Adding an intensity-corroboration signal (intensity held while volume falls ⇒ deliberate) is the open follow-up in TODOS.md — until then the copy carries the ambiguity rather than resolving it wrongly.
- **FTP history** — `Models/StoredFTPSnapshot.swift`. Use `StoredFTPSnapshot.resolved(for:snapshots:)` to get the FTP value in effect for any historical workout date. Default 200W when no snapshot exists.
- **7-day forecast** — `Views/Recovery/ReadinessForecastChart.swift` + `ReadinessRepository.compute7DayForecast()`. Requires 14 days of `StoredDailyScore`. The HARD/MED/EASY/REST label is `max(byRecovery, byLoad)` over `ForecastEffort` (ordered least → most restrictive), **not** the recovery score alone — a well-recovered athlete mid-ramp was told "Hard effort OK" while the Load tab said to take rest days. The load ceiling is computed **per forecast day** by asking `calculateReadiness(referenceDate: end of that day)` with only existing workouts: the forecast assumes no further training, so the acute window empties and the ceiling relaxes across the horizon (ACWR>1.5 → ceiling `.easy`; 1.3–1.5 → `.moderate`). Load is a **ceiling, never a floor** — it must not upgrade a poor-recovery day. This label also feeds `MasterCoachEngine.StateVector.nextDayForecast`. Test-fixture gotcha: forecast day 1 is *tomorrow* and its window closes at the end of tomorrow, so the oldest acute day has already rolled off — a ramp needs ~3h/day to clear ACWR 1.5 there, not 2h.
- **Workout load calculation** — `Services/Analytics/PredictiveReadinessService.calculateWorkoutLoad()` uses three-path priority: zone-weighted power → NP/avg-power TSS → duration × sport multiplier. Path 1 runs only when `StoredWorkout.powerZoneSeconds` decodes, which is nil before the stream is fetched, for a ride with no watts stream (`SyncManager.noPowerStreamCSV`, or a `noPowerStreamRetryMarker` while the ride awaits its one retry), and when all seven zones sum to 0 (a power-meter dropout); such a ride falls to path 2 or 3 instead of scoring 0 load. New zone consumers must read the decoder, not `powerZoneSecondsCSV`.
- **One ACWR engine** (v0.1.10.0). Every Load surface must get its ACWR and per-workout load from `PredictiveReadinessService` (`calculateReadiness` / `calculateWorkoutLoad`). `TrainingLoadVisualizationService` delegates to it and holds no load math of its own — a duration-only `hours × 100` TSS there once made "Extended Analysis" report ACWR 1.80/Overreaching while the Load tab said 1.33/Building. The status thresholds live in two switches (`ReadinessAssessment.Trend` and `TrainingLoadVisualizationService.loadStatus(for:)`) that MUST stay in lockstep: detraining `<0.8` / optimal `0.8–1.3` / building `1.3–1.5` / overreaching(danger) `>1.5`. `Trend` has four cases — adding a fifth is a compile error across `UnifiedTrainingLoadCard`, `ACWRTrendCard`, `InsightsView`.
- **`TrainingLoadCalculator` bands on the canonical ACWR, not `ewmaRatio`**. Its TSS / EWMA / monotony / strain metrics are its own, but `status` and `recommendation` come from `PredictiveReadinessService.calculateReadiness(...).acwr`. Banding on `ewmaRatio` made the Load Details card print "Training load is elevated" (canonical ACWR 1.3–1.5) directly above the lightbulb line "Training load is optimal and recovery is good" (EWMA ≤1.3) on the same screen — the two ratios sit a full band apart in practice (ACWR 1.40 → EWMA banded it *overreaching*). `ewmaRatio` stays on the struct as a display value; don't reconnect it to band selection. Covered by `testLoadSummaryStatusAgreesWithAssessmentTier`.
- **A day's ACWR window closes at the END of that day**. Every daily ACWR point goes through `PredictiveReadinessService.windowEnd(for:now:)` — past days close at the following midnight, today closes at `now`. Passing `startOfDay(day)` closes the window *before* that day's training: the 7-day trend chart's last point ignored today's ride (rendering exactly 1.0 for a steady-load user) while the assessment printed beside it included it, and every earlier point was shifted a day late. The 7-day trend (`ReadinessRepository.calculateImprovedACWRTrend`) and the 90-day series (`TrainingLoadVisualizationService.generateTimeSeriesData`) both delegate to it — don't reintroduce a local reference-date rule in either. Test gotcha: `TrainingLoadACWRConsistencyTests.workout(daysAgo:)` offsets by `daysAgo − 0.5` *days from now*, so it does NOT land on calendar day `today − daysAgo` — any assertion about which day a workout falls in must build its date from `startOfDay(today)` explicitly.
- **ACWR history chart cold-start** (v0.1.10.0). `TrainingLoadVisualizationService.generateTimeSeriesData` trims the series to `earliestWorkout + 28 days` — a day whose 28-day chronic window predates the data fabricates `(acute/7)/(chronic/28) = 4.0`. `ReadinessRepository` reads **118 days** of workouts (`loadHistoryWorkoutDescriptor`, 90-day window + 28-day lead-in) for the visualization so the trimmed chart fills a full 90 days, not 62. Do not narrow this read back to 90 or the chart loses a month. Consequence for tests: any fixture that asserts on `timeSeriesData`/`summary.currentStatus` needs **>28 days of history before today** (`TrainingLoadACWRConsistencyTests.fixture` carries a 29–56-day lead-in) — exactly 28 days rounds the first valid chart day to *tomorrow* and yields an empty series ("Unknown" status), a wall-clock-date flake.
- **Intent breakdown joins on `originalId`, not `WorkoutData.id`**. `WorkoutData(from:)` derives `id` via `WorkoutData.stableID(from:)`: HealthKit ids (already UUID strings) pass through unchanged; non-UUID Strava ids get a deterministic RFC 4122 v5 UUID (namespace `1B4E28BA-2FA1-11D2-883F-0016D3CCA427`). `originalId` (== `StoredWorkout.id`) is the authoritative key for any join against `StoredIntentLabel` or stored data — `TrainingLoadVisualizationService.calculateIntentBreakdown` MUST key on it. The old `id.uuidString` join minted a throwaway UUID per Strava workout and silently dumped ≈79% of load into `.other`/"Unclassified". Do not add new joins on `WorkoutData.id`. (`EnhancedIntentAwareReadinessService` is safe — it operates on `[StoredWorkout]`.)
- **Load-by-intent intensity is signal-derived, never duration**. `TrainingLoadVisualizationService.estimateIntensity` scores 1–10 from power-zone-weighted IF → NP/avg-power ÷ FTP → HR ÷ 185 → neutral 5.0 (no fabrication when signal is absent). Do NOT revert to the old duration heuristic (`4 + hours×1.5`) — it reported every ~1h ride as ~5.x regardless of effort. Anchors: IF 0.40→1, 1.20→10; HR 50%→1, 100%→10.
- **Strain sensitivity** — `CardiovascularStrainService.compute(sensitivityOffset:)`. Offset read from `UserDefaults["strainSensitivityOffset"]` (range −0.2 to +0.2, default 0.0). Normalization constant is 70.0.
- **HeuristicIntentClassifier** — power-zone path takes priority over HR for cycling when `powerZoneSeconds` stream data is present. Only classifies workouts owned by the user (not third-party HealthKit sources).
- **WorkoutAuditView** — debug view in Settings → Today's Workouts showing all stored workouts with source, FTP, and zone data.

## Known Compiler Patterns

### SourceKit "Cannot find X in scope" — always noise
SourceKit reports false "Cannot find type/member in scope" errors throughout this project because it analyzes files in isolation without the full module graph. These are **not real build errors**. Only trust errors that appear in an actual Xcode build (`xcodebuild`) or from the Swift compiler directly.

### "Compiler unable to type-check expression in reasonable time" — `body` too large
When a SwiftUI `body` triggers this error, decompose it into:
- `private var mainView: some View` — owns the top-level container + background
- `@ToolbarContentBuilder private var toolbarItems: some ToolbarContent` — owns toolbar items
- Keep `body` as a thin modifier chain only

Applied to: `RecoveryDashboardView.swift`

### `.foregroundStyle(.tokenName)` type inference failures
In batch-compile contexts Swift sometimes fails to resolve shorthand `.tokenName` for custom `Color` extensions. Always use explicit `Color.tokenName` form (e.g. `Color.accent`, `Color.statusOptimal`) — never the dot-shorthand.

### `ForEach` with named tuple arrays — `Binding<C>` overload always wins
iOS 26.2 SwiftUI's compiler picks `ForEach.init<C>(_ data: Binding<C>, ...)` over `RandomAccessCollection` when named tuples are involved, regardless of input type. Fix: define a local `struct … : Identifiable` inside the View and use `ForEach(array) { item in }`.

Applied to: `InsightsView.swift` → `DataCollectionCard.ActivitySummary`

## Recovery Science Model

This section defines the physiological constraints for all recovery and strain calculations.
Do not deviate from these decisions without explicit user approval.

### Guiding principle
The app targets weekend warriors who feel their body but don't have a sports scientist.
Coaching language should reflect lived experience ("you're still paying off yesterday's ride"),
not raw numbers. Always translate scores into plain-English guidance.

### Carry-forward fatigue
Recovery is not a same-day phenomenon. A hard workout creates physiological debt —
elevated muscle damage, depleted glycogen, suppressed HRV — that persists 24–48+ hours.

- `RecoveryDecayService` must carry forward prior-day fatigue into today's baseline.
- The intra-day energy chart must start from this morning's readiness score (which already
  reflects prior-day strain), not from a neutral 100-point baseline.
- "No workout today" does not mean "fully recovered." It means fatigue is decaying passively.

### Steps and non-exercise activity load (NEAT)

**Scientific basis:**
- The 10,000-step target has no clinical foundation (1960s Japanese pedometer marketing).
- I-Min Lee (Harvard, 2019): all-cause mortality curve flattens ~7,500 steps; diminishing
  returns beyond that for sedentary-baseline populations.
- Steps represent mechanical load and metabolic expenditure that compounds with training stress.

**Threshold rule — personal baseline, not a fixed number:**
- Steps contribute to strain only above the user's 30-day rolling average daily step count.
- A person who habitually walks 12,000 steps/day is not accumulating extra stress at 12,000.
- A person who averages 4,000 steps/day and hikes 14,000 is accumulating real load.
- Never hardcode 7,500 or 10,000 as a universal goal or threshold.

**Contribution curve:**
- Ramp is non-linear: going from 18,000→20,000 steps is harder than 8,000→10,000.
- Use a mild linear ramp above threshold, capped so steps never exceed 20% of total daily strain.
- Steps are supporting load, not primary training stress. A hard interval session always dominates.

**Mechanism 1 — steps add to intra-day strain curve:**
- Compute excess steps = max(0, today_steps − 30day_avg_steps). Baseline fallback when no history: 5000 steps.
- Convert: `todayStepExcessTSS = min(excessSteps / 3000.0, cap)` where cap = 20% of today's workout TSS, or 2.0 on rest days.
- Pass `todayStepExcessTSS` to `RecoveryDecayService.calculateIntraDayReadiness` — it adds directly to the intra-day fatigue accumulation alongside workout TSS.

**Mechanism 2 — high daily movement reduces overnight recovery rate:**
- Only activates when combined load (workout strain + step excess) exceeds a threshold.
- Implemented as a percentage reduction on overnight recovery rate, not a flat points deduction.
  This preserves the relationship: 9hrs sleep > 5hrs sleep, even on high-load days.
- Has a floor: cannot reduce recovery rate below 50% of normal, regardless of step count.
- Does not activate on step excess alone — walking without training stress does not impair recovery.

**What steps do NOT do:**
- Steps do not directly set or cap the readiness score.
- Steps are never shown as a "goal to hit" in coaching language. The app does not reward
  10,000 steps. If steps are displayed, frame them as load context, not achievement.

### Energy Bank chart intent
The chart shows dynamic readiness across a full day (midnight to midnight):
- Solid line = elapsed time (actual fatigue state)
- Dashed line = projected remainder of day assuming no further workouts
- Y-axis starts from this morning's readiness baseline (carry-forward), not 100
- A rest day after a hard workout should show gradual upward slope, not a flat line

### Recovery model hierarchy (highest to lowest influence)
1. Overnight HRV and resting HR (primary recovery signal)
2. Sleep duration and quality
3. Prior-day workout strain (carry-forward fatigue)
4. Today's workout strain
5. NEAT / excess steps (supporting modifier)
