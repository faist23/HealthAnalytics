## Approach Selected

**A — Full Design Doc:** BGProcessingTask + TrainingPattern SwiftData model + all 3
pattern types (block crash cycle, HRV precursor, sleep fragmentation) + push
notifications on first detection.

Rationale for choosing A over B (In-Process First): The BGProcessingTask architecture
is the correct long-term design. The user explicitly wants the complete architecture.
Complexity is manageable (~7 files). The background scheduling reliability concern is
real but mitigable with proper fallback (run analysis on-demand if BGTask fires too
infrequently).

### Sub-service Coupling Pattern

`TrainingDNAAnalyzer` follows the exact same pattern as `InjuryRiskCalculator` in
`ReadinessRepository.swift` — a `private let trainingDNAAnalyzer = TrainingDNAAnalyzer()`
property. Not injected, not nested. The instance lives inside `ReadinessRepository` and
is called from `runPatternAnalysis(context:)`. No direct ViewModel access.

**Testability seam:** `TrainingDNAAnalyzer` exposes:
```swift
protocol PatternDataProvider { /* fetchACWR, fetchHRV, fetchSleep, fetchSickDayProxies */ }
struct LivePatternDataProvider: PatternDataProvider { /* HealthKit + SwiftData impl */ }

class TrainingDNAAnalyzer {
    init(dataProvider: PatternDataProvider = LivePatternDataProvider()) { ... }
}
```
`ReadinessRepository` uses `private let trainingDNAAnalyzer = TrainingDNAAnalyzer()` —
the no-arg call resolves to `LivePatternDataProvider` via the default. Tests inject a
fixture: `TrainingDNAAnalyzer(dataProvider: FixturePatternDataProvider(acwrHistory: ...))`.
This allows testing pattern detection logic against controlled 180-day datasets without
HealthKit. This is the minimum seam needed; do not over-engineer it.

### Data Flow

```
BGProcessingTask fires (device idle + charging)  ─OR─
User opens InsightsView and lastPatternAnalysisDate > 7 days ago (fallback)
  └─▶ ReadinessRepository.runPatternAnalysis(context:)
        ├─▶ Update UserDefaults["lastPatternAnalysisDate"] = Date()
        └─▶ TrainingDNAAnalyzer.analyze(context:)
              ├─▶ fetchACWRHistory(180 days) → block crash detection
              ├─▶ fetchHRVHistory(180 days) + fetchSickDayProxies() → HRV precursor
              │     NOTE: fetchSickDayProxies() uses activity gap detection — days where
              │     HKWorkout count drops to 0 AND step count falls below 2,000 after
              │     an active streak (≥3 consecutive workout days). This is the passive
              │     sick-day proxy for Phase 2a. Walking steadiness (HKCategoryTypeIdentifier
              │     AppleWalkingSteadinessEvent) is a FALL RISK metric, not illness proxy —
              │     do NOT use it here. Phase 2a uses only step/workout gaps.
              │     Phase 2a uses HealthKit passive detection ONLY.
              │     Manual illness log (Phase 2b) is NOT implemented here.
              │     If sick day events are empty, Pattern Type 2 is silently skipped.
              └─▶ fetchSleepHistory(180 days) → sleep fragmentation
              └─▶ [TrainingPattern] → dedup by patternType before persisting
                    └─▶ PatternNotificationService.notifyIfNew([TrainingPattern])

Fallback trigger: InsightsView.onAppear checks
  UserDefaults["lastPatternAnalysisDate"] — if nil or > 7 days ago, calls
  ReadinessRepository.runPatternAnalysis(context:) inline.
```

### TrainingPattern Model

Minimum deployment target: iOS 26+. SwiftData `[Date]` array fully supported.

```swift
enum PatternType: String, Codable {
    case blockCrashCycle
    case hrvPrecursor          // corrected from hvPrecursor
    case sleepFragmentation
}

@Model
class TrainingPattern {
    var patternType: PatternType         // blockCrashCycle | hrvPrecursor | sleepFragmentation
    var detectedAt: Date
    var confidenceNumerator: Int         // e.g. 3
    var confidenceDenominator: Int       // e.g. 4
    var evidenceSummary: String          // human-readable coach voice
    var citationKey: String              // maps to CitationDatabase
    var instanceDates: [Date]            // when each instance occurred (for timeline dot plot)
    var coachingResponse: String         // actionable adjustment suggestion
    var notificationSent: Bool           // prevent duplicate notifications
}
```

Notification deduplication: `PatternNotificationService.notifyIfNew()` queries SwiftData
for an existing `TrainingPattern` with matching `patternType` where `notificationSent == true`
before sending. Prevents duplicate notifications across analysis runs.

**Upsert semantics:** One canonical `TrainingPattern` per `patternType`. Each analysis run:
- Fetch existing record where `patternType == currentType`
- If found: update `detectedAt`, `confidenceNumerator`, `confidenceDenominator`,
  `instanceDates` (replace, not merge), `evidenceSummary`, `coachingResponse`.
  Preserve `notificationSent` — never reset it once true.
- If not found: create new record with `notificationSent = false`.

`coachingResponse` is computed by `TrainingDNAAnalyzer` and stored in the model at
analysis time (not at display time) because it includes a comparison to athlete's current
load numbers. It must be refreshed on each analysis run.

### BGProcessingTask Registration

Identifier: `com.craigfaist.HealthAnalytics.patternAnalysis`

**Architecture inversion (per spec review):** `InsightsView.onAppear` is the PRIMARY
analysis trigger. `BGProcessingTask` is OPPORTUNISTIC background refresh. Rationale:
BGTask fires at most once per day under ideal conditions (idle + charging + Wi-Fi) and
often less on heavy-use devices. Most users experience pattern detection through the
onAppear path. BGTask is a nice-to-have that keeps patterns fresh without app open.

**Primary path:** `InsightsView.onAppear` checks `UserDefaults["lastPatternAnalysisDate"]`.
If nil or > 7 days ago, calls `ReadinessRepository.runPatternAnalysis(context:)` async
before rendering the Training DNA section. Shows a loading state.

**Background path (iOS 26+ API):** Use the `.backgroundTask` SwiftUI modifier in the
`@main` App struct — NOT the legacy `BGTaskScheduler.shared.register(forTaskWithIdentifier:...)`
pattern. iOS 26 / WWDC 2025 promotes this as the idiomatic approach.

```swift
@main
struct HealthAnalyticsApp: App {
    var body: some Scene {
        WindowGroup { ... }
            .backgroundTask(.appRefresh("com.craigfaist.HealthAnalytics.patternAnalysis")) {
                await ReadinessRepository.shared.runPatternAnalysis(container: modelContainer)
            }
    }
}
```

Scheduling: call `BGTaskScheduler.shared.submit(BGAppRefreshTaskRequest(...))` after the
app backgrounds (in `.onChange(of: scenePhase)` where `newPhase == .background`).
Set `earliestBeginDate` to 24h from now.

Expiration: The `.backgroundTask` modifier handles cancellation automatically when the
system reclaims time. `runPatternAnalysis` must be structured as cooperative async/await
so cancellation propagates naturally — do not persist a partially-analyzed `TrainingPattern`
if the task is cancelled mid-flight (check `Task.isCancelled` before each `modelContext.save()`).

**HealthKit auth:** `ReadinessRepository.runPatternAnalysis` must check `HKHealthStore`
authorization status for required types before analysis. If denied: set `analysisError`
and surface "HealthKit access required for pattern analysis" in the Training DNA section
(reuse the existing `analysisError` flow).

## Confidence Display Language

- 2 instances (sleep fragmentation only, at minimum threshold): "Early signal · seen in 2 of 2 periods"
- 3 instances: "Tentative · seen in 3 of 3 [blocks/events/periods]"
- 4 instances, all matching: "Consistent · seen in 4 of 4 [blocks/events/periods]"
- 5+, ≥75% match: "Consistent · seen in X of Y [blocks/events/periods]"
- 5+, <75% match: "Mixed signal · seen in X of Y [blocks/events/periods]"

The noun ("blocks" / "events" / "periods") is pattern-type specific — set as a property on
each pattern type enum case. No percentages. Fraction only + plain English qualifier.

## Data Gates

| Pattern type | Minimum instances | First analysis gate |
|---|---|---|
| Block crash cycle | 3 complete blocks | 90 days |
| HRV precursor | 3 correlated illness events | 90 days |
| Sleep fragmentation | 2 distinct training periods | 60 days |

Section visibility rule: Training DNA section hidden entirely if total HealthKit history
< 60 days (the minimum gate for any pattern type). No placeholder card.
At 60-89 days: only sleep fragmentation may surface (if 2+ periods detected).
At 90+ days: all three pattern types may surface (subject to per-type gates above).

## Notifications

**Permission request:** `PatternNotificationService.requestAuthorizationIfNeeded()` called
once on app launch (in `@main` App struct). On denial, notifications are silently skipped —
no retry prompt, no UI indicator. The pattern card is shown regardless; the notification is
just a bonus discovery mechanism.

One notification per pattern type, ever. `notificationSent: Bool` on `TrainingPattern`
model prevents re-sending. Copy examples:
- Block crash cycle: "Training DNA found: you consistently overreach in week 3 of your
  training blocks. Open the app to see the pattern."
- HRV precursor: "Training DNA found: your HRV drops 36-72h before illness — you
  have a detectable warning signature."

## UI Design Specifications (Design Review Pass — 2026-03-27)

### TrainingDNACard Anatomy

Cards use `Color.surface` background, `Color.accentBorder` 1pt stroke, `md` (16pt) corner
radius, `md` (16pt) internal padding, `lg` (24pt) vertical spacing between cards.

**Card structure top-to-bottom:**

```
┌──────────────────────────────────────────┐
│ [icon] Pattern Name            [share]   │  ← Header row
│  One-line pattern definition             │  ← Subtitle
│──────────────────────────────────────────│
│  Consistent · seen in 4 of 4 blocks      │  ← Confidence line
│  ● ●   ●      ●   ●●  ●                  │  ← Timeline (44pt)
│  90d ago                          Now    │  ← Axis labels
│──────────────────────────────────────────│
│  evidenceSummary text here...            │  ← Diagnostic
│                                          │
│ ▌ coachingResponse text here...          │  ← Prescriptive (accent border)
└──────────────────────────────────────────┘
```

**Header row:** Pattern name in `.font(.system(size: 17, weight: .semibold, design: .default))`
`Color.textPrimary`. Icon at 20pt colored with pattern-type token (see below). ShareLink
icon (`square.and.arrow.up`, 24pt, `Color.textSecondary`) trailing-aligned with 16pt padding.

**Pattern subtitle:** One-line definition in `.font(.system(size: 13, weight: .regular, design: .default))`
`Color.textSecondary`. Appears below the header row, above the divider.

**Confidence line:** Qualifier ("Consistent ·", "Tentative ·", etc.) in
`.font(.system(size: 13, weight: .medium, design: .default))` `Color.textSecondary`.
Count ("seen in 4 of 4 training blocks") in same spec, `Color.textPrimary`. Inline.

**evidenceSummary:** `.font(.system(size: 15, weight: .regular, design: .default))`
`Color.textSecondary`. The "here's what your data showed" voice.

**coachingResponse:** `.font(.system(size: 15, weight: .regular, design: .default))`
`Color.textPrimary`. Preceded by a 3pt leading border rule in `Color.accent` with 8pt
leading padding (SwiftUI: `.overlay(alignment: .leading) { Rectangle().fill(Color.accent).frame(width: 3) }`
inside a padded HStack). Visually signals "this is action, not description."

**Coaching freshness:** `detectedAt` displayed as relative time ("Updated 3 days ago") in
`.font(.system(size: 11, weight: .regular, design: .monospaced))` `Color.textTertiary`
below `coachingResponse`. This is a timestamp = Mono is correct per design system rules.

**"New" badge:** When `detectedAt` is within 48h AND the user has not yet tapped the card:
a "New" pill badge (`Color.accent` text, `Color.accentDim` background, `sm` 8pt radius,
`Color.accentBorder` border) in the top-trailing of the header row. Dismiss on first tap.
Implement via a `@AppStorage` key keyed on `patternType.rawValue + "_seen"`.

## Key Implementation Notes (from section review + outside voice)

### Architecture Mandate
`TrainingDNAAnalyzer` is a `@ModelActor` background actor owned by `ReadinessRepository` as a
`private let` property. InsightsView → InsightsViewModel → ReadinessRepository.runPatternAnalysis
→ TrainingDNAAnalyzer. The mandate is satisfied. TrainingDNAAnalyzer NEVER communicates
with ViewModels directly.

**InsightsView reads patterns reactively:** `@Query var patterns: [TrainingPattern]` in
`InsightsView` — SwiftData reactive reads, no `@Published` intermediary needed on
`ReadinessRepository` for pattern display.

**InsightsViewModel integration point:** `InsightsViewModel.analyzeData()` must call
`ReadinessRepository.shared.runPatternAnalysis(container:)` for pattern analysis.
This is the bridge between the existing InsightsViewModel flow and the new pattern engine.

### @ModelActor (iOS 26+ Idiomatic)
`TrainingDNAAnalyzer` uses `@ModelActor` (NOT manual `actor` + `newBackgroundContext()`).
iOS 26+ automatically provides `modelContext` inside `@ModelActor` — no manual context
management needed. `ReadinessRepository (@MainActor)` calls `await trainingDNAAnalyzer.analyze()`.

```swift
@ModelActor
actor TrainingDNAAnalyzer {
    let dataProvider: PatternDataProvider

    init(modelContainer: ModelContainer, dataProvider: PatternDataProvider = LivePatternDataProvider()) {
        // modelContext is automatically provided by @ModelActor
        self.dataProvider = dataProvider
    }

    func analyze() async throws -> [TrainingPattern] { ... }
}
```

`modelContext.save()` MUST be wrapped in `do/catch` — silent failure on disk-full or
corruption would lose analysis results without any user-visible error.

### ModelContext Save Contract
```swift
do {
    try modelContext.save()
} catch {
    // surface error via ReadinessRepository.analysisError
    throw PatternAnalysisError.persistenceFailed(error)
}
```
Never call `modelContext.save()` outside a `do/catch`. Silent SwiftData write failures
are the most common source of invisible data loss.

### StatisticalValidator Reuse
`StatisticalValidator.swift` (existing) should be reused inside `TrainingDNAAnalyzer`
for p-value gating on pattern confidence. Don't duplicate statistical testing code.

**CRITICAL — call once per pattern type, at end of detection only.** `StatisticalValidator.bootstrapConfidenceInterval()` uses 10,000 iterations by default. Calling it per-sample will exhaust the BGTask time budget (~30s). The correct pattern:
1. Collect all candidate instance dates for a pattern type
2. Run pattern-specific detection logic across all instances
3. Call `StatisticalValidator` ONCE on the full candidate set
4. Accept or reject the pattern based on p-value gate

### HealthKit Query Strategy
Use `HKStatisticsCollectionQuery` with daily aggregation buckets for all metric fetches (ACWR, HRV, sleep, steps). Do NOT use raw `HKSampleQuery` for bulk history — too many samples, too slow. Daily aggregation keeps BGTask within budget.

```swift
// Shared DRY helper — avoids duplicating query setup across fetchACWR, fetchHRV, fetchSleep
private func fetchDailyMetric(
    type: HKQuantityType,
    unit: HKUnit,
    startDate: Date,
    options: HKStatisticsOptions
) async throws -> [Date: Double] { ... }
```

Use this helper for all three pattern types. Do not copy-paste query setup code.

### analyze() throws Contract
`TrainingDNAAnalyzer.analyze()` must be declared `throws`. Callers wrap in `do/catch` and
surface errors via `ReadinessRepository.analysisError`. Never silently swallow HealthKit
query failures or persistence errors inside the analyzer.

### Sick Day Proxy (corrected)
Step count < 2,000 for 2+ CONSECUTIVE days AND no logged workout in that window
(ruling out intentional rest days). Single-day rest day false positives eliminated.

### BGTask Entitlement
`com.apple.developer.background-task` entitlement must be added to the app's entitlements
file AND `BGTaskSchedulerPermittedIdentifiers` array added to Info.plist BEFORE any
BGTask testing is possible. This is a provisioning/profile change, not a code change.
Do this FIRST.

### No-Blocks Fallback
When analysis runs but no qualifying blocks found (inconsistent training history):
"Training DNA analyzing — your training blocks aren't long enough yet to detect a
crash cycle. Keep training consistently." Same quiet-row treatment as near-threshold.

### Manual Refresh Button
InsightsView's existing `arrow.clockwise` refresh button (in toolbar) should also
reset `UserDefaults["lastPatternAnalysisDate"]` to nil and trigger pattern analysis,
not just correlation analysis. Consistent UX.

### Section Visibility Summary
See **UI Design Specifications → Section Visibility States** above for the full reconciled table.
Short form: hidden < 45d, informational row 45-59d, sleep frag possible at 60-89d, all patterns at 90+.
